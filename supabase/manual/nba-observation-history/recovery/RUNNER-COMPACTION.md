# Physical reclamation after logical cleanup — separate approval

The runner never calls VACUUM, REINDEX, CHECKPOINT, pg_repack, or any physical compaction. A successful logical run leaves 68,772 history rows and 34,386 unchanged current rows, but PostgreSQL can still retain the old heap/index allocation. Do not judge physical recovery from deletion count alone.

After the runner's full final verification and after separately reviewing current disk/WAL/old-transaction/replication metrics:

1. Approve ordinary standalone vacuum to make deleted tuple/index space reusable. It must not be wrapped in BEGIN/COMMIT:

   ```sql
   VACUUM (ANALYZE, INDEX_CLEANUP ON, TRUNCATE FALSE, PARALLEL 0)
   public.nba_player_game_observation_versions;
   ```

2. Measure heap, indexes, total database size, physical `/data` availability and WAL again. Do not assume vacuum shrinks the heap; original latest observations remain near its end. Keep space reserved for unrelated live activity and the new operation's WAL/workspace.

3. If there is verified reserve beyond the predicted **small live replacement**, the simplest complete compaction is one separately approved standalone operation:

   ```sql
   VACUUM (FULL, ANALYZE) public.nba_player_game_observation_versions;
   ```

   This preserves the table identity/dependencies and rebuilds its indexes. The new heap/indexes contain the 68,772 live rows, not a second full copy of all 1.5 million old records. The old files still exist until completion, and WAL/sort workspace need additional capacity. It holds ACCESS EXCLUSIVE on history, so plan a short observation-history maintenance window. No separate automatic REINDEX afterward.

4. If that headroom is insufficient, review individual index rebuilds generated by `reindex-commands.sql`. Rebuilding one index at a time may return much of the old ~430 MiB index allocation before the heap rewrite. Each rebuild still requires its own new index/workspace/WAL and can block reads using the index. Check capacity between operations. Do not perform it if its own reserve cannot fit; arrange extra capacity/Supabase assistance instead.

5. Recheck current checksum/reference/latest integrity, every retained boundary, trigger states, constraint/index validity and actual database/disk/WAL size. Check existing NBA analytics, Player Center, live scores/rosters and historical scoring behavior. Resume normal factual ingestion and monitor its next scheduled run; do not trigger ingestion automatically.

`pg_repack` is not a low-headroom shortcut: it requires an extension/client and substantial temporary space. Do not swap/drop/truncate the live tables, bypass FKs, rewrite immutable data to force relocation, drop replication slots, or change WAL settings as part of this runner.

Based on the earlier production allocation, a compacted database might be around 230–300 MB if other data stays stable. That is an estimate, not a guarantee. Database quota, used filesystem space, WAL and provisioned disk size are different metrics. Operator-run long maintenance should use an approved direct/session PostgreSQL client session or Supabase assistance rather than relying on the SQL Editor's upstream request timeout.
