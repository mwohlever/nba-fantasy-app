# NBA Player Center factual refresh

Implemented locally October 29, 2026. No production SQL, ingestion, deployment, workflow activation, mapping application or maintenance was performed. Existing projection-retirement/Player Center changes are retained, and unrelated work is preserved. This supersedes the old shadow-worker resume instructions and direct-insert staging approach in the dated rollout documents. Frozen October 23 bundles remain unchanged as evidence, not current apply instructions.

## Data flow

The manual-only `NBA Player Center factual refresh` workflow uses the existing workflow file and concurrency group, existing GitHub secret and production domain. Execution defaults to **false**. There is no cron declaration. It invokes `scripts/run-nba-player-center-refresh.cjs`; the old worker and NBA shadow ingest route are retired, so they cannot bypass atomic cache/status publication. The existing local removal of forecast generators, consumers, forecast-only routes and NFL generation jobs remains in place. NFL factual ingestion, actual NBA/NFL scoring, Groups, frozen slate rules and saved snapshots remain separate.

The worker freezes all active NBA catalog entries, exact reviewed identities, one explicit NBA season, a common game-selection cutoff, run UUID, pool hash and workflow commit. Resolved identities get a game-log and regular-season-summary GET; unresolved/conflicting entries become explicit blocked status rows without provider calls. It validates/fetches incrementally and publishes bounded batches. Default mode is the current NBA ending year, with October 1 UTC rollover, and `prior` is an explicit correction mode. An explicit historical ending year is also available. Future seasons are refused.

`lib/player-center/nbaRefresh.ts` shares the existing game-log, season-stat and observation normalizers. Complete final positive-minute regular-season core facts go through the existing semantic append RPC. DNP, live, unknown and nullable richer statistics remain in the raw season snapshot, not manufactured zero-stat observations. Ordinary acquisitions use real fetched time as known time. No observation or retained first-known timestamp is advanced for an unchanged poll. An `as_of` cutoff selects the game universe; it does not claim that corrections fetched later were known at that earlier instant.

The new `publish_player_center_nba_refresh` RPC wraps `append_nba_projection_observations` unchanged. In one transaction it checks identity/season, run order, bounded raw data and current/cache agreement, appends legitimate versions, publishes a compatible season-cache row when available, and updates latest refresh status. One batch accepts at most five players and 3 MB; observation calls remain <=200 rows. Cache JSON is capped at 512 KiB per player. The worker also splits by a 2.5 MB request budget.

Publication is serialized and fenced against older cutoffs or changed same-run replay payloads. Exact replay validates the JSONB receipt and skips writes, preserving cache/status timestamps. A dropped HTTP acknowledgement is resolved by replay of the original checkpoint, not a fresh acquisition or blind write retry. A failed batch rolls back its facts, cache and status together; previous committed batches remain reported. All existing history triggers, references and the original append source body remain unchanged. Preflight/publication rejects a changed append body using the reviewed source MD5 `9308a04b52fecc6993b7730490cf686a`.

A valid log may add independently verified facts when a summary request fails, but it cannot certify coverage or refresh a complete cache. Transport/shape failures retain the previous cache/check timestamp and record failure status. Recognized partial snapshots are stored as incomplete. Rich shooting/summary corrections can update the latest cache while adding zero core observation versions. The core observation history continues to cover minutes and six scoring stats; the richer cache does not promise time-travel history for every shooting field or season summary.

## Status and coverage

The existing `player_center_season_cache` is reused. One additional table stores **latest status per player-season**, not append-only fetch history: current outcome, attempt/acquisition/verification timestamps, independent counts, original receipt, appended count and the latest failure timestamp/issues. Successful recovery preserves the last failure metadata for diagnosis.

Outcomes are `verified_data`, `verified_zero_appearances`, `coverage_incomplete`, `acquisition_failed`, and `blocked_identity`. Only complete independently verified coverage advances `last_verified_at`. A failed check does not advance the retained cache's `checked_at`; a valid partial acquisition can be fresh but is not rankable. Detailed run/checkpoint evidence is retained as GitHub artifacts for 14 days rather than duplicated in the database.

NBA readers validate UUID-based publications against their status row. A missing, failed, superseded or inconsistent status blocks comparison eligibility; a retained old snapshot is explicitly stale. Legacy owner-reviewed bootstrap receipts remain compatible. The existing full-pool/common-cutoff/per-metric gates, missing-last short samples and Group/frozen scoring remain authoritative. No per-player ESPN fetch is introduced on comparison or draft-page requests. Raw facts never contain persisted Group fantasy scores or forecasts.

The runtime comparison universe remains the complete active catalog for the requested sport/position. The known 530-player pool has 367 resolved identities; applying the dated 98 candidates would still leave 65 unresolved. No identity is guessed or active flag changed to manufacture full coverage. Unknown rows keep sorting alphabetical. Explicit GP=0 and genuinely complete short samples remain missing-last without blocking fully covered peers. Last 3/5 never borrow older-season games or skip unknown recent appearances.

## The 45 ESPN no-data cases

Reduced public-response fixtures cover all 45 failed player-season pairs from Actions run 40789028481, across 44 players. The independent read-only investigation captured 90 responses: all logs were HTTP 200 with only league filters and no requested season/events; 43 summaries had no exact-season GP evidence, and two summaries for ESPN 5061603 also lacked phase evidence. None established GP=0.

They remain `acquisition_failed` with `unverified_no_data`, never zero. Verified zero requires an explicit exact-season regular-season GP=0 and no contradictory appearance evidence. Conflicting NBA GP categories or ambiguous multi-team totals withhold coverage. Wrong league, season, athlete or phase is rejected. Resolving the real cases requires fresh identity/native-season evidence or better provider evidence, not a weaker parser or fallback to NCAA/prior years.

The offline `review-nba-refresh-identities.cjs` tool now audits existing mappings as well as new candidates and labels stale evidence. It never applies mappings. Against the **dated October 23 snapshot**, 337 existing claims are corroborated, 30 existing claims require renewed review, 98 are mapping candidates, and 65 remain unresolved. These are not new production findings. The existing snapshot preparation command now accepts the NBA season helper and a `--snapshot-only` mode, so new evidence need not pass the old frozen 98-row apply-plan assumptions.

## Operational safeguards

- Current/prior modes are implemented, but all scheduling remains unconfigured pending approval. Intended policy: nightly current season while active and through a 30-day correction settling period; weekly offseason and previous-season corrections; older seasons only through explicit reviewed work. Previous-season full-pool cache publication needs the same independent evidence/common cutoff. The current/prior reader freshness rules remain 24 hours/seven days; a delayed job may deliberately leave rankings unavailable.
- At most two concurrent GETs, paced at 40/minute, 10-second request timeouts, 3 MB streamed response caps, one retry for transient HTTP/timeouts, and <=25% total retry allowance. Invalid success payloads are not blind-retried. Ten consecutive unverified acquisitions open the circuit after saving completed failure statuses. Incomplete/unresolved/failure arrays produce a non-clean exit; green cannot mean `failed` was ignored.
- The soft processing limit is 40 minutes; the workflow limit is 45. A full 530-player log+summary pass needs about 27 minutes at 40/minute before retries, so the former 15-minute limit was unsuitable. An early stop leaves an explicit checkpoint, not a claim of full coverage.
- Production CLI writes require `--execute`, GitHub Actions, `main`, an allowed event, checkout SHA matching `GITHUB_SHA`, the intended production domain and project, and passing schema/storage checks. It never loads local credentials or `.env`. Resume requires the same commit, pool, mode, season and original payloads. Workflow `resume_run` downloads the original report artifact; no automatic whole-run retry exists.
- The SQL/API expose only bounded health aggregates to service_role. Server-side metrics use the existing service key; it is not returned or logged. Fresh /data metrics are compared with live SQL database/WAL figures; missing/stale/disagreeing metrics stop publication.
- Physical disk reserve: **256 MiB**, plus **64 MiB WAL/concurrent-write allowance** and six times the bounded payload. The measured workload is far smaller, but allowance is not a hard PostgreSQL peak guarantee. Database warning: **400 MB decimal**; publication stops before **450 MB**, including a bounded heap allowance. Combined season-cache/status allocated-space cap: **64 MiB**. These are conservative launch limits, not instructions to prune data or force a run through storage pressure.
- Source-correctness, reference/latest-current checks, RPC body hash, counts, checksums and storage are recorded. Reports distinguish accepted input, actual appends, replay/non-appending input, verified/blocked/incomplete/failed players and committed receipts. Unchanged per-game TOAST JSON is preserved while successful check metadata advances, reducing poll-only cache churn too.

## Local storage evidence

`data/player-center/nba-refresh-storage-benchmark.json` records an isolated PostgreSQL 17 benchmark. It duplicates an actual captured 60-game NBA history into a **synthetic** 530-player cohort; it does not certify 530 real players or production compression. The measured values are approximately 23.31 MiB logical / 3.51 MiB allocated initially; three metadata-only checks reach 5.30 MiB; three additional forced full-payload rewrites reach 15.44 MiB without relying on a vacuum operation. An 82-game logical extrapolation is 31.86 MiB, not a measured full-season production size. Actual future production sizes remain gated by the limits above.

The 512 KiB per-player ceiling alone could allow roughly 278 MB across 530 players, exceeding the free-tier allowance when added to the existing database. It is not used as a total budget. Measure actual allocation, TOAST/index growth, WAL and normal autovacuum behavior during controlled verification; do not add automatic deletion, VACUUM FULL or index rebuilds to this job.
